# Ship thin plugins, distrust Desktop hooks

The plugin-marketplace-plus-thin-template design is the right shape. None of the surveyed starter kits has it, and it fixes the template rot that every clone-and-copy kit suffers. Its weak point is the platform: the kit's safety and sync behaviour depends on hooks, and hooks are the least reliable part of Claude Code in the Desktop app's Code tab on Windows. An open bug with a reproduction (#96496) says project, user and plugin hooks do not fire there at all. Desktop on Windows has also failed to register `extraKnownMarketplaces` (#70318, folded into the still-open #16870). Three of the plan's guard designs are wrong even when hooks do fire. A Stop hook runs after every reply, not once at session end. A `Bash`-only matcher never sees the PowerShell tool, which Claude treats as the primary shell on Windows. A hook that returns "ask" has no blocking effect in auto mode. The evidence therefore moves enforcement away from hooks and onto permission `deny` rules, which apply in every mode, plus Claude Code's classifier-based auto mode. Auto mode is now available on all plans, appears in the Desktop mode selector, and blocks force-push, hard reset and remote rewrites out of the box. For a non-technical user it beats acceptEdits plus an allowlist, but it cannot be set from project settings and it is not a security boundary. On the side decisions: OpenKnowledge is credible but too young on Windows, so the Obsidian fallback should become the default. 1Password Individual supports vault-scoped service accounts under a 1,000-requests-per-day account cap, the ~$36/yr price is a first-year promo, and unencrypted Bitwarden JSON cannot be imported. nvm-windows requests elevation despite its "user" scope, so fnm should replace it. Every claim about Desktop-on-Windows behaviour below needs confirming on the Windows VM before the kit ships.

## Prior art converges on one shape and fails on one problem

Non-developer Claude Code starter kits have settled on a recognisable formula: a folder skeleton, a short CLAUDE.md, five to ten slash-command skills, an auto-commit hook so the user never touches git, and a first-run onboarding command. The two most popular examples are Obsidian "second brain" vaults. **heyitsnoah/claudesidian (2.6k stars)** onboards with a `/init-bootstrap` wizard that installs dependencies, imports an existing vault, writes a personalised CLAUDE.md and initialises git ([claudesidian](https://github.com/heyitsnoah/claudesidian)). **ballred/obsidian-claude-pkm (1.9k stars)** ships ten skills, four agents, a coach output style, a PostToolUse auto-commit hook and a Windows `setup.bat` ([obsidian-claude-pkm](https://github.com/ballred/obsidian-claude-pkm)). Both last pushed before mid-2026. A wave of near-zero-star vault templates appeared in late 2026 and adds nothing structurally new. At the other end, **davila7/claude-code-templates (33k stars)** is a copy-files registry of roughly 1,900 components installed by `npx` ([claude-code-templates](https://github.com/davila7/claude-code-templates)). For a beginner that much breadth is exactly the skill-sprawl problem.

Every one of these kits ships by clone or copy, so seeded files stop updating after day one. claudesidian's wizard deliberately "Disconnect[s] from the original claudesidian repository", which cuts the user off from upstream fixes for good ([claudesidian](https://github.com/heyitsnoah/claudesidian)). obsidian-claude-pkm patches the same problem with an `/upgrade` skill that updates "preserving your content" ([obsidian-claude-pkm](https://github.com/ballred/obsidian-claude-pkm)). The beep-beginners split, with logic in an auto-updating plugin and only a thin seed in the template repo, is a structural fix that none of the surveyed kits uses. **No public kit targets the Desktop Code tab on Windows.** Every onboarding guide read assumes a terminal.

The closest match to the planned onboarding plugin is **moatazeldebsy/onboarding-kit** (0 stars, created 2026-10-18), and its design choices are worth copying more than its popularity suggests ([onboarding-kit](https://github.com/moatazeldebsy/onboarding-kit)). It asks two questions and saves a profile so it never asks again. It runs a read-only machine check where "nothing runs until you say yes". It merges safe defaults into settings only after taking a timestamped backup, never overwrites an existing CLAUDE.md, and gives "Beginners… [no plugins] on purpose". It ends with one consolidated list of changes that the user approves in one go. It also tells users to disable the kit after setup because it "adds a few hundred tokens to every session". On native Windows its bash doctor falls back to `claude doctor`, which is a direct warning against bash in our kit. Matt Pocock's `wizard` skill contributes the other half of the pattern: a staged, idempotent script that "opens each URL, says exactly what to click and copy… confirms at every stage, and shows how many stages are left" ([wizard SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/wizard/SKILL.md)). **No surveyed kit installs Windows software unattended.** They all detect, explain and ask.

Matt Pocock's skills repo (316k stars) is a dependency candidate. Its README tells Claude Code users to install `mattpocock-skills@claude-plugins-official`, which "updates itself by default" ([mattpocock/skills](https://github.com/mattpocock/skills)). The official marketplace needs no `extraKnownMarketplaces` entry: an `enabledPlugins` key is enough ([org plugins](https://code.claude.com/docs/en/plugins/org.md)). Two details matter. First, `git-guardrails-claude-code` sits in `skills/misc/` and is **not** in the plugin's 27-path `skills` array, so plugin users do not get it ([plugin.json](https://github.com/mattpocock/skills/blob/main/.claude-plugin/plugin.json)). Second, his `grill-me` is a thin user-invoked alias (`disable-model-invocation: true`) whose whole body calls the model-invoked `grilling` skill ([grill-me](https://github.com/mattpocock/skills/blob/main/skills/productivity/grill-me/SKILL.md)). That gives a beginner an explicit slash command while keeping one implementation.

The marketplace mechanics settle two design rules. **Only relative-path plugin entries load from project settings with no per-user install**. An external `github` source leaves every user stuck at `Plugin "<name>" is enabled in project settings but isn't installed` until they run `claude plugin install … --scope project` ([org plugins](https://code.claude.com/docs/en/plugins/org.md)). Separately, **third-party marketplaces do not auto-update by default**, and `marketplace.json` has no field to turn it on ([host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md)). The template's `extraKnownMarketplaces` entry must set `"autoUpdate": true`. The plugins should also omit `version` so the commit SHA becomes the version, because "a manifest that pins `"version": "1.0.0"` keeps every user on the cached copy until its author changes the string" ([plugin loading](https://code.claude.com/docs/en/plugins/loading.md)). Durable plugin state belongs in `${CLAUDE_PLUGIN_DATA}`, since `${CLAUDE_PLUGIN_ROOT}` changes with every version. Instruction files should stay **under 200 lines**, because "longer files consume more context and reduce adherence", and CLAUDE.md is "context, not enforced configuration" ([Memory](https://code.claude.com/docs/en/memory)).

**Adopt**
- One marketplace repo whose plugins are all relative-path entries, with a distinctive marketplace `name` and entry names identical to each `plugin.json` name.
- `"autoUpdate": true` on the template's `extraKnownMarketplaces` entry, and no `version` field (or a CI-enforced version bump).
- A thin template: AGENTS.md under 200 lines, a CLAUDE.md that only imports `@AGENTS.md`, folders and settings. Everything else lives in plugins.
- An onboarding plugin built on onboarding-kit's pattern: read-only doctor first, profile or state in `${CLAUDE_PLUGIN_DATA}` or a visible checklist file, one consolidated approval, backups before merges, and no retrying around failures. Add Pocock-style "step N of M" stages, with exact click instructions, for the steps only a human can do.
- Five or fewer beginner-facing skills, as user-invoked aliases over model-invoked implementations.
- `mattpocock-skills@claude-plugins-official` enabled in `enabledPlugins` instead of vendoring the skills.

**Avoid**
- External-source plugin entries for anything the template enables.
- Copy-files installers and "disconnect from upstream" wizards.
- A pinned `version` without a bump discipline, or `version` set in both `plugin.json` and the marketplace entry.
- Large catalogs or many always-on plugins for a beginner. Check `claude plugin details` for always-on token cost.
- Relying on Pocock's `git-guardrails-claude-code` through his plugin, since it isn't shipped there.
- Unattended software installs.

## Desktop Code mode honors the settings on paper and drops hooks in practice

The documentation describes full parity. Desktop "and CLI read the same configuration files", "Hooks and skills defined in settings apply to both", and local Code-tab sessions have a plugin browser (**+ → Add plugins / Manage plugins**) with user, project and local scope ([Desktop](https://code.claude.com/docs/en/desktop)). The hooks reference says Claude Code "fires the same hook events wherever it runs", Desktop included ([Hooks](https://code.claude.com/docs/en/hooks)). One documented exception affects the kit directly: "Plugins aren't available in WSL sessions", which removes WSL, and with it the only OS-level sandbox on a Windows machine ([Desktop](https://code.claude.com/docs/en/desktop); [Sandboxing](https://code.claude.com/docs/en/sandboxing)).

The bug tracker contradicts the documented parity. **#96496** (open, labelled bug, has repro, area:hooks and area:desktop, created 2026-09-23) reports that SessionStart, Stop, PreToolUse and PostToolUse hooks in a project's `.claude/settings.json` fire in terminal `claude` but not in the Desktop Code tab. A Windows commenter adds that user-settings hooks "never fire in the desktop Code tab" and appears to say plugin hooks fail too ([#96496](https://github.com/anthropics/claude-code/issues/96496)). An earlier Windows 11 report, #51904, found plugin PostToolUse hooks firing in the CLI but silently not in Desktop and blamed a `--setting-sources user` launch ([#51904](https://github.com/anthropics/claude-code/issues/51904)). Marketplace registration has its own gap: **#70318** (Windows 11) reports that the Desktop app "fails to register the marketplace in the local plugin registry". The reported workaround is to run `/plugin marketplace add` once in the CLI on the same machine, after which Desktop picks it up ([#70318](https://github.com/anthropics/claude-code/issues/70318)). That issue was closed as a duplicate of **#16870**, which is still open and has a commenter reporting that project `extraKnownMarketplaces` plus `enabledPlugins` "does nothing" ([#16870](https://github.com/anthropics/claude-code/issues/16870)). Anthropic has said nothing on #96496 and no fix version was found. Desktop also runs "its own copy of Claude Code, which has its own version number", so a fix shipped to the CLI does not reach the Code tab until Desktop updates ([Desktop](https://code.claude.com/docs/en/desktop)).

Trust gating adds one more silent failure path. "The `extraKnownMarketplaces` entries apply only in a folder the contributor has trusted, and in an untrusted folder Claude Code ignores them without a message", and project `permissions.allow` rules wait for the trust dialog as well ([org plugins](https://code.claude.com/docs/en/plugins/org.md); [Permissions](https://code.claude.com/docs/en/permissions)). **No document says whether the Desktop Code tab shows a workspace trust dialog**, or how it records trust. A one-time CLI bootstrap therefore gives the kit three things: it accepts trust, registers the marketplace, and installs at project scope. Desktop then inherits that state through the shared `~/.claude` registry ([Install plugins](https://code.claude.com/docs/en/plugins/install.md)).

Even where hooks do fire, Windows has fail-open traps, and three of them break the plan's hooks as designed. The first is the PowerShell tool. "On Windows, wherever the PowerShell tool is enabled, Claude treats PowerShell as the primary shell and routes shell commands through it." Without Git Bash, Claude Code "doesn't register the Bash tool at all. A hook that matches only `Bash` never fires there" ([Hooks](https://code.claude.com/docs/en/hooks)). The PowerShell tool is on by default for claude.ai accounts when Git for Windows is installed ([Setup](https://code.claude.com/docs/en/setup)). **A `Bash`-only git guard or secret-path matcher misses most shell commands on this user's machine.** The second is the Stop hook, which runs at the end of every turn. Its exit 2 "Prevents Claude from stopping" ([Hooks](https://code.claude.com/docs/en/hooks)). A `git push` there pushes after every reply. Hook commands are not reviewed by the permission system or the auto-mode classifier, so the push also bypasses any `ask` rule on `git push`. The third is interpreter failure, which is silent. The Microsoft Store `python3` alias exits 49 with no output, so a PreToolUse guard fails open (#57946) ([#57946](https://github.com/anthropics/claude-code/issues/57946)). `shell: "powershell"` hooks spawn `pwsh` with no fallback to `powershell.exe`, so on a stock box they never run, and "cannot return 2 — it fails open" (#90077) ([#90077](https://github.com/anthropics/claude-code/issues/90077)). On Windows 11 with Git Bash, hook processes have been left suspended for 30 to 60+ minutes, with "55 of them alive at once" (#77078) ([#77078](https://github.com/anthropics/claude-code/issues/77078)). Paths also arrive with backslashes, so a forward-slash comparison "never matches… and the tool call proceeds" ([Hooks](https://code.claude.com/docs/en/hooks)). A guard that times out does not block unless `"onFailure": "block"` is set (v2.1.295+) ([Hooks](https://code.claude.com/docs/en/hooks)).

The documented mitigations point to exec form. Set `"command"` to a real `.exe` and pass `args`. That skips the shell and its quoting, and the docs explicitly prefer it "for any hook that references a path placeholder" ([Hooks](https://code.claude.com/docs/en/hooks)). With `uv`, that means `"command": "uv"` (or an absolute `uv.exe`) and `"args": ["run","--script","${CLAUDE_PLUGIN_ROOT}/hooks/guard.py"]`. This avoids the `python3` stub and may also avoid the MSYS path implicated in #77078, but nobody has verified it on Windows Desktop. Desktop "doesn't read PowerShell profiles", so `uv` must be on the user or system PATH, and Desktop must be fully quit and reopened after it is installed ([Desktop](https://code.claude.com/docs/en/desktop)).

**Adopt**
- Git for Windows as a hard prerequisite (the Bash tool, the Monitor tool and worktree sessions need it), with every shell guard and permission rule written for both `Bash` and `PowerShell`.
- Exec-form hooks invoking `uv.exe` with PEP 723 scripts, `onFailure: "block"` on security guards, short timeouts on everything else, and backslash-to-slash normalisation before any path check.
- A one-time CLI bootstrap in the repo (`claude`, accept trust, `claude plugin marketplace add`, `claude plugin install … --scope project`) as a documented onboarding step, not an emergency workaround.
- A visible "guards active" signal from SessionStart, so a non-firing hook is noticeable. It is subject to the same bug, so a missing banner is itself the diagnostic.
- Treating hooks as defense in depth behind permission `deny` rules, which do not depend on the hook runtime.

**Avoid**
- Any design where a hook is the sole protector of secrets, git history or sync.
- A Stop-hook `git push`.
- `Bash`-only matchers, bare `python3`, `shell: "powershell"`, shell-form hooks with unquoted placeholders, and symlinked skill directories.
- Desktop WSL sessions.

## Auto mode beats prompt fatigue but is not a fence

Auto mode is now a mainstream setting, not a preview. "A separate classifier model reviews actions before they run, blocking anything that escalates beyond your request, targets unrecognized infrastructure, or appears driven by hostile content Claude read" ([Permission modes](https://code.claude.com/docs/en/permission-modes)). It is available on all plans with Opus 4.6+, Sonnet 4.6+, Haiku 5.5 or Fable models. Since v2.1.283 it is the built-in starting mode for terminal and VS Code sessions, and it requires v2.1.233+ on native Windows. In Desktop it appears in the mode selector "when auto mode is available; there is no separate Settings toggle for it" ([Desktop](https://code.claude.com/docs/en/desktop)). Desktop users reported bundled versions of 2.1.270 to 2.1.304 in September and October issues, which suggests the Code tab clears the version floor. That still needs confirming with `/status` on the VM.

The default block list covers most of what the planned git guard was meant to catch: "Force push", "`git reset --hard`, `git checkout -- .`, `git restore .`, `git clean -fd`, `git stash drop`", "Changing where pushes go with `git remote set-url` or `git remote add`", `curl | bash`, and "Sending sensitive data to external endpoints" ([Permission modes](https://code.claude.com/docs/en/permission-modes)). Deny rules still block and ask rules still prompt, but broad allow rules such as `Bash(*)`, `PowerShell(*)` and wildcarded interpreters are dropped while auto is on. Two defaults run against the kit's intent. **Auto mode allows "Pushing to any branch of the repository you're working in, including the default branch"**, and it allows "reading `.env` and sending credentials to their matching API" ([Permission modes](https://code.claude.com/docs/en/permission-modes)). After three consecutive blocks, or 20 in total, it pauses and resumes prompting.

The honest numbers come from Anthropic's own engineering post. Across 10,000 real actions the full pipeline had a **0.4% false-positive rate**. On 52 real "overeager" actions it had a **17% false-negative rate**, which the post calls "the honest number", and 5.7% on synthetic exfiltration. The post concludes that auto mode "is not a drop-in replacement for careful human review on high-stakes infrastructure" ([Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)).

So does it beat acceptEdits plus an allowlist, a deny list and hooks? For this user, yes, and the Desktop hook bug makes the case stronger. acceptEdits still prompts for every shell command outside the allowlist. A non-technical user will approve those prompts without reading them, and one guide for non-engineers names "reading every permission prompt like it was a legal document" as a pain point ([claudecode-lab](https://claudecode-lab.com/en/blog/claude-code-for-non-engineers/)). An unread prompt is not a control. The planned hooks may not fire in the Code tab at all. The classifier runs inside the harness, so it does not depend on the hook runtime that #96496 breaks. It catches the `git -C . push --force`-style variants that text rules miss. The permissions docs admit `Bash(git push *)` doesn't stop "`git -C . push origin main`… `git 'push' origin main`" and that such rules aren't "a security boundary around the program" ([Permissions](https://code.claude.com/docs/en/permissions)). Auto mode has three costs. It cannot be shipped in the repo: "If you set `"auto"` in `.claude/settings.json`… the value doesn't take effect". It must come from `~/.claude/settings.json`, managed settings, or one pick in the Desktop selector, which "is remembered per folder and outranks a `defaultMode` in the project's `.claude/` settings" ([Permission modes](https://code.claude.com/docs/en/permission-modes)). Hook "ask" decisions do not block in auto mode, as reproduced on Windows 11 with a `Bash|PowerShell` matcher (#89561) ([#89561](https://github.com/anthropics/claude-code/issues/89561)). And with no sandbox on native Windows, a 17% miss rate on overeager actions sits directly on the user's files.

The right architecture layers the defences instead of choosing between them. Auto mode is the everyday mode. Explicit `deny` rules are the hard floor, and they need PowerShell twins for a specific reason: "On Windows with Git Bash installed, denying Bash also turns the PowerShell tool off for the session… Claude Code turns PowerShell off without a warning" unless a scoped `PowerShell(...)` rule exists ([Tools reference](https://code.claude.com/docs/en/tools-reference)). `ask` rules cover the human checkpoints auto mode would otherwise allow, such as pushing to `main`. Hooks deny with exit 2 and add value when they fire. The deny list has known limits: Read and Edit denies don't apply "to arbitrary subprocesses that read or write files indirectly, like a Python or Node script", or to `grep -r` ([Permissions](https://code.claude.com/docs/en/permissions)). The secret-path guard therefore stays best-effort on Windows whatever the mode.

**Adopt**
- Auto mode as the recommended everyday mode, set by the onboarding plugin writing `defaultMode: "auto"` to `~/.claude/settings.json` (with a backup), or by the user picking Auto once per folder in the Desktop selector. Verify the result in the selector before the first message.
- Project `deny` rules as the enforcement floor: `Read(.env)`, `Read(.env.*)`, `Read(**/secrets/**)`, `Edit(.env)`, force-push and hard-reset patterns. Mirror each one as a `PowerShell(...)` rule.
- `ask` rules for `git push` to the default branch, if a human checkpoint there is wanted.
- PreToolUse guards that return `deny` or exit 2, never `ask`, and that parse git argv properly (`-C`, `-c`, quoting, `+refspec` force pushes).
- Optional managed settings with `disableBypassPermissionsMode: "disable"` if the author wants bypass to be non-overridable.

**Avoid**
- `defaultMode: "auto"` or `"bypassPermissions"` in the repo's `.claude/settings.json`. The first silently falls back to the built-in default and the second starts in Manual.
- Describing auto mode to the user as "safe". Anthropic says it "does not guarantee safety".
- A large allowlist. Broad allow rules are dropped in auto mode anyway, and in acceptEdits they become a rubber stamp.
- Scoped `Bash(...)` deny rules without PowerShell twins, unless switching the PowerShell tool off is deliberate.

## OpenKnowledge is promising but Obsidian should be the default

OpenKnowledge is real and well engineered. It is a GPL-3.0, "local-first, open-source Markdown editor built for people and agents to work in the same files", backed by plain markdown in a git folder, with a built-in MCP server exposing 19 tools ([openknowledge.ai](https://openknowledge.ai); [MCP reference](https://github.com/inkeep/open-knowledge/blob/main/docs/content/reference/mcp.mdx)). Its Windows installer is per-user under `%LOCALAPPDATA%\Programs\` with no admin prompt. Its privacy default is that "Nothing about your content leaves your machine by default" ([what OpenKnowledge writes](https://github.com/inkeep/open-knowledge/blob/main/docs/content/reference/what-open-knowledge-writes.mdx)).

Its maturity is the problem. The repo was created on 2026-06-03 and is still on 0.x, with **eight stable releases between 2026-10-28 and 2026-11-04** (v0.88.10 to v0.89.3) and beta builds in between ([releases](https://github.com/inkeep/open-knowledge/releases)). Windows desktop support only arrived in early August 2026, when issues #656 and #1116 closed ([#1116](https://github.com/inkeep/open-knowledge/issues/1116)). The tracker shows an open Windows atomic-rename bug (#2066), plus closed data-integrity bugs where an MCP edit "returns success… but never writes to disk" (#2086) and a move could overwrite its destination with an empty document (#1714) ([issue search](https://github.com/inkeep/open-knowledge/issues?q=windows)). It also writes project MCP registrations (`.mcp.json`, `.cursor/mcp.json`, `.codex/config.toml`, `opencode.json`, `.pi/extensions/…`) "regardless of what's installed". It registers itself for `.md` files under `HKCU`, "which can make it the default opener", and uninstalling "does not restore a previous file-type default" ([what OpenKnowledge writes](https://github.com/inkeep/open-knowledge/blob/main/docs/content/reference/what-open-knowledge-writes.mdx)). For a user who cannot read a git diff, unexplained config files and a hijacked `.md` association are support tickets. It has **no winget package**, so it falls outside the `tools.yaml` installer path.

Obsidian has none of these problems. It installs with `Obsidian.Obsidian` with explicit user scope (`/currentuser`) ([winget manifest](https://github.com/microsoft/winget-pkgs/tree/master/manifests/o/Obsidian/Obsidian)), keeps one `.obsidian` config folder in the vault ([Obsidian Help](https://obsidian.md/help/configuration-folder)), and "is free for all purposes, including personal, commercial, and non-profit use" ([Obsidian license](https://obsidian.md/license)). It has no MCP server, and Claude Code does not need one to read and write markdown files. **The plan's OpenKnowledge-immaturity trigger for the Obsidian fallback is already met.**

**Adopt**
- Obsidian as the default editor, installed with `winget install -e --id Obsidian.Obsidian --scope user`.
- A `.gitignore` covering `.obsidian/workspace.json` and `workspace-mobile.json`, or all of `.obsidian/`. This follows common practice; Obsidian's docs don't cover git.
- OpenKnowledge as an operator-side tool, with a re-evaluation once its Windows build has gone a few months without data-integrity bugs.

**Avoid**
- OpenKnowledge as the primary editor for the non-technical user today.
- If it is used anyway: blanket-ignoring `.ok/`, since `.ok/config.yml` is meant to be committed and `.ok/.gitignore` already excludes the PII-bearing local files ([init-project.ts](https://github.com/inkeep/open-knowledge/blob/main/packages/server/src/init-project.ts)). Also avoid letting its agent-config files land in commits unexamined.

## 1Password Individual works, with a daily cap and a promo price

Service accounts appear on Individual and Families in 1Password's own rate-limit table: **1,000 reads and 100 writes per hour per token, and 1,000 requests per day per account**. Teams gets 5,000 per day and Business 50,000 ([rate limits](https://www.1password.dev/service-accounts/rate-limits/)). No 1Password page found says "service accounts are available on Individual" in so many words. Availability is inferred from that table, so check the account's Developer page before building on it. Service accounts can be scoped per vault, but "You can't give a service account access to your built-in Personal, Private, or Employee vault, or to your default Shared vault", and permissions and vault access are immutable after creation ([get started](https://www.1password.dev/service-accounts/get-started/)). A dedicated vault must exist before the token is minted. The 1,000-per-day cap applies across the whole account, so a hook or loop that resolves secrets on every command will run out of quota.

For interactive work, the CLI desktop integration is the better route. It requires 1Password for Windows, Windows Hello, and the "Integrate with 1Password CLI" toggle under Settings > Developer ([CLI app integration](https://www.1password.dev/cli/app-integration/)). Authorisation "expires after 10 minutes of inactivity" with a 12-hour hard limit and is scoped to each terminal window ([security model](https://www.1password.dev/cli/app-integration-security)). The user should expect repeated Hello prompts and be told they are normal. The SSH agent requires disabling the Windows "OpenSSH Authentication Agent" service, which takes admin rights once. After that, 1Password listens on `\\.\pipe\openssh-ssh-agent`, and Git should be pointed at `C:/Windows/System32/OpenSSH/ssh.exe` ([SSH get started](https://www.1password.dev/ssh/get-started/)).

Two facts in the brief need correcting. **Unencrypted Bitwarden JSON is not importable**: 1Password accepts only Bitwarden's password-protected "`.json (Encrypted)`" export. It accepts that in the apps or on 1Password.com, CSV only in the apps, and passkeys and shared-collection items are not imported ([import from Bitwarden](https://support.1password.com/import-bitwarden/)). Users have hit "No codec found" errors even with encrypted exports, and one flagged Bitwarden's Argon2id KDF as a possible gap ([community thread](https://1password.community/discussion/146166/importing-from-a-bitwarden-vault-fails-no-codec-found)). **The ~$36/yr Individual price is a first-year promo**: $2.99/mo billed yearly for new direct annual customers, then the regular $3.99/mo (about $47.88/yr). Families is $4.49/mo promo and $5.99/mo regular ([pricing](https://1password.com/pricing/password-manager)).

**Adopt**
- 1Password Individual, budgeted at the regular ~$48/yr, with Windows Hello and CLI desktop integration (`op run` with `op://` references) for interactive secrets.
- A dedicated "Claude" vault created before any service account, and at most one read-only, vault-scoped service account, used only for unattended runs.
- Bitwarden migration through the encrypted JSON export on 1Password.com, falling back to CSV in the Windows app, with the export file deleted afterwards.

**Avoid**
- Resolving secrets inside per-tool-call hooks.
- Granting a service account broad scope "for now", since scope cannot be changed later.
- Promising the user a $36 annual cost.
- Leaving the Windows OpenSSH Authentication Agent service running alongside 1Password's agent.

## Most tools install per-user, and the exceptions cluster into one UAC batch

All `tools.yaml` entries were checked against live `microsoft/winget-pkgs` manifests on 2026-11-06. Every tool has a verified id except OpenKnowledge, Gemini CLI and a Grok consumer chat app. The portable and zip packages (Claude Code, uv, Bun, `op`, Codex, `grok`, fnm, CLIProxyAPI) install per-user with no UAC. uv, Codex and Grok Build pull in the machine-scope `Microsoft.VCRedist.2015+.x64` dependency, which may prompt if it is missing ([uv manifest](https://github.com/microsoft/winget-pkgs/blob/master/manifests/a/astral-sh/uv/0.13.7/astral-sh.uv.installer.yaml)). The nvm-windows row is the clearest clash with a "user-scope first" manifest. Its manifest declares `Scope: user` and `ElevationRequirement: elevatesSelf` at the same time. The project's own README now promotes a successor with "No mandatory administrator privileges" and "Shim mode - no symlinks", which implies the current tool does need them ([nvm-windows](https://github.com/coreybutler/nvm-windows)). fnm is zip-portable with no elevation. For the install script, use `winget install -e --id <Id> --source winget --accept-package-agreements --accept-source-agreements --disable-interactivity --scope user|machine` ([winget install](https://learn.microsoft.com/en-us/windows/package-manager/winget/install)). Treat `0x8A15002B` (no applicable update) and `0x8A150061` (already installed) as success, and catch `0x8A150056` (installer prohibits elevation) as the symptom of running a user-scope package from an elevated shell ([return codes](https://github.com/microsoft/winget-cli/blob/master/doc/windows/package-manager/winget/returnCodes.md)). The machine-scope set (Tailscale, VS Build Tools, Python if machine, VCRedist, the OpenSSH capability, and disabling the Windows ssh-agent service for 1Password) can run from one elevated script, so the user sees a single UAC prompt. After installs, refresh PATH from the registry, and fully restart Desktop, because Desktop reads only the user and system environment at launch.

The remote-help channel needs a different design from the one implied by "Tailscale SSH". **Tailscale SSH's server component runs only on Linux and macOS**, so a Windows machine can only be a client ([Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)). The working combination is Windows' built-in OpenSSH Server reached over Tailscale. Installing it "creates and enables a firewall rule named `OpenSSH-Server-In-TCP`" that opens port 22 on every interface ([OpenSSH first use](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_install_firstuse)). That rule should be replaced with one scoped to Tailscale's range (for example `-RemoteAddress 100.64.0.0/10`), which is this research's own design and not vendor guidance. Do not pin `ListenAddress`, because Tailscale may not be up at boot unless Run Unattended is on ([Run unattended](https://tailscale.com/kb/1088/run-unattended)). The most common failure is key placement. For an administrator account, which this user almost certainly has, sshd reads `C:\ProgramData\ssh\administrators_authorized_keys`, ACL'd to SYSTEM and Administrators only, and ignores `~\.ssh\authorized_keys` ([OpenSSH config](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-server-configuration)). The user then shares the machine into the helper's tailnet. The recipient must be an Owner, Admin or IT admin there, and the shared node "can receive incoming connections… but cannot start connections" ([Sharing](https://tailscale.com/kb/1084/sharing)). Node keys expire after 180 days by default. RDP hosting requires Windows Pro ([Remote Desktop](https://support.microsoft.com/en-us/windows/how-to-use-remote-desktop-5fe128d5-8fb1-7a23-3b8a-41e636865e8c)). Quick Assist is the edition-agnostic GUI fallback: "The helper must have a Microsoft account. The sharer doesn't have to authenticate", and the helper still depends on the user to answer UAC prompts ([Quick Assist](https://learn.microsoft.com/en-us/windows/client-management/client-tools/quick-assist)).

**Adopt**
- fnm for Node, `uv python install` for Python, `Google.Chrome.EXE` for user-scope Chrome, the 1Password msix, the portable `gh`, and the native Claude Code installer (or a scheduled `winget upgrade`).
- One elevated batch for the machine-scope set, user-scope installs in the normal session, `--source winget` on every call, and success-equivalent exit codes handled explicitly.
- Tailscale with Run Unattended, OpenSSH Server with key-only auth (`PasswordAuthentication no`, lowercase `AllowUsers`), the key in `administrators_authorized_keys` with the documented `icacls`, a Tailscale-scoped firewall rule, and the default rule disabled. Node sharing goes into the helper's tailnet, with Quick Assist as the GUI fallback.

**Avoid**
- nvm-windows and Volta in a user-scope-first manifest.
- Running user-scope installs from an elevated shell.
- Relying on winget for Claude Code updates.
- Tailscale SSH on the Windows host, RDP on Home, `ListenAddress` pinning, and the default all-interface port-22 rule.

## Implications for the settled decisions

Six of the plan's decisions are strained by this evidence, and two of them break.

**Hooks as the enforcement layer (strained hardest).** The PreToolUse git guard, the secret-path block and the listing checker all assume hooks run in the Desktop Code tab. #96496 says they don't, with a Windows confirmation, and nothing indicates a fix ([#96496](https://github.com/anthropics/claude-code/issues/96496)). The decision survives only as defense in depth. Primary enforcement moves to permission `deny` rules plus auto mode's classifier, and a SessionStart banner makes hook failure visible.

**Stop or session-end `git push` (breaks).** Stop fires after every reply, its exit 2 keeps Claude working, and hook commands bypass both the permission system and the classifier ([Hooks](https://code.claude.com/docs/en/hooks)). On Windows it is also exposed to the suspended-process hang in #77078. SessionEnd is a better-fitting event, but it is subject to the same Desktop bug. Replace the push hook with an explicit plain-language `/save` or `/ship` skill, and let Claude run `git push` under deny and ask rules and classifier review. Auto mode already allows pushes to the working repo, including `main`.

**Bash-only matchers (breaks).** On Windows the PowerShell tool is primary when enabled, and without Git Bash the Bash tool doesn't exist ([Hooks](https://code.claude.com/docs/en/hooks)). Every matcher becomes `Bash|PowerShell`, and every scoped `Bash(...)` deny needs a `PowerShell(...)` twin, or PowerShell silently switches off ([Tools reference](https://code.claude.com/docs/en/tools-reference)).

**acceptEdits plus allowlist as the default mode (strained).** Auto mode is available, it does not depend on hooks firing, and it removes the prompts a non-technical user would rubber-stamp. The decision should flip to auto mode set at user level, with project `acceptEdits` kept as the fallback for accounts or models where auto is unavailable. Guards must deny rather than ask (#89561) ([#89561](https://github.com/anthropics/claude-code/issues/89561)).

**Repo-declared marketplace "just works" after clone (strained).** Trust gating is silent, Desktop's trust dialog is undocumented, and #70318/#16870 show Desktop not registering repo marketplaces ([#70318](https://github.com/anthropics/claude-code/issues/70318)). Make the one-time CLI bootstrap a required onboarding stage. Keep plugins relative-path, with `autoUpdate: true`.

**OpenKnowledge as primary editor (fallback triggered).** It is 0.x, Windows support is three months old, it has had data-integrity bugs, it writes agent config into the repo, and it has no winget id ([releases](https://github.com/inkeep/open-knowledge/releases)). Obsidian becomes the default.

**1Password at ~$36/yr with service accounts (strained on cost and design).** The price is the first-year promo; the regular price is $47.88 ([pricing](https://1password.com/pricing/password-manager)). The service account must target a dedicated non-Personal vault, decided up front, under a 1,000-per-day account cap ([rate limits](https://www.1password.dev/service-accounts/rate-limits/)). The Bitwarden migration step must specify the encrypted JSON export.

**nvm-windows in tools.yaml (strained).** It requests elevation despite user scope ([manifest](https://github.com/microsoft/winget-pkgs/blob/master/manifests/c/CoreyButler/NVMforWindows/1.2.2/CoreyButler.NVMforWindows.installer.yaml)). Swap it for fnm. Similarly, a winget-installed Claude Code never auto-updates.

**Tailscale SSH for remote help (breaks on Windows).** Replace it with OpenSSH Server over Tailscale, using the admin-keys file and a scoped firewall rule.

### Must be proven empirically on the Windows VM

1. Whether the Desktop Code tab shows a workspace trust dialog for a freshly cloned template, and whether project `extraKnownMarketplaces` and `enabledPlugins` load relative-path plugins with no CLI step. Repeat after the CLI bootstrap.
2. Whether project, user and plugin hooks fire in the Desktop Code tab for SessionStart, PreToolUse, PostToolUse, Stop and SessionEnd. Test with and without Git for Windows, and record the bundled version from `/status`.
3. Which shell runs shell-form hooks with and without Git Bash, and whether exec-form `uv run --script` hooks avoid the #77078 suspension. Include measured first-run latency against the hook timeout.
4. That `onFailure: "block"` actually blocks when `uv` is missing from PATH, and that a deny-returning guard blocks under auto mode.
5. That a `Bash|PowerShell` guard sees PowerShell-tool commands, and that `PowerShell(...)` deny twins keep the PowerShell tool enabled.
6. That auto mode appears in the Desktop selector for the user's plan and model, that a user-level `defaultMode: "auto"` is honored, and that the per-folder pick sticks. Run a red-team pass: force-push, `git -C . push`, `+main` refspec, `.env` read through a Python one-liner, and `grep -r`.
7. Whether `autoUpdate: true` in project `extraKnownMarketplaces` triggers the "Plugin updated" notice in Desktop after a pushed commit.
8. Whether Desktop picks up `uv`, `fnm` and `git` from the user PATH after a full quit and reopen, and whether the `python` Store alias intercepts anything.
9. The user-scope winget runs: Git.Git `--scope user` elevation, GitHub.cli portable selection, Anthropic.Claude msix versus exe selection and UAC, VCRedist prompts, and exit codes on re-run.
10. The 1Password items: service-account creation on Individual, the Bitwarden encrypted-JSON import with an Argon2id vault, and the Windows Hello prompt cadence under `op run` from the Code tab.
11. The remote-help chain: OpenSSH key auth via `administrators_authorized_keys`, the Tailscale-scoped firewall rule, the actual adapter alias, sshd reachability after reboot with Run Unattended, a node share into the helper's tailnet, and Quick Assist on Windows 11 Home.

## Conclusion

The kit's distribution design is ahead of the field. Its enforcement design was written for the terminal Claude Code and has to be rebuilt for the Desktop Code tab. Given which pieces actually work in Desktop today, the order of trust inverts. Settings-file deny rules and the harness-internal classifier become the load-bearing controls, and hooks become a visible bonus layer whose silence is itself a signal. That inversion also simplifies the kit. A beginner needs fewer moving parts when sync is an explicit skill, the editor is Obsidian, and the mode is auto with a short deny list.

The VM test plan now matters more than any remaining research. Several facts that decide the architecture are undocumented and can only be settled by testing: Desktop trust, Desktop hook firing, and Desktop marketplace registration. The two open bugs could close in any Desktop release. Build the kit so it works safely if hooks never fire, and gets better when they do.
